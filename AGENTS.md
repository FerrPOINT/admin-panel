# Правила работы в Admin Panel

## Текущий статус

Реализация v1 запущена: Rust API (backend/), React UI (frontend/) и docker-compose.dev.yml (7771 API, 7772 web, 7773 PostgreSQL). Тесты: backend — cargo test в контейнере rust:1.88; frontend — pnpm test. Изменения вендорятся только через план в docs/plans/. Не выдавайте проект за работающий сервис и не добавляйте код или конфигурацию, если задача явно не переводит проект к реализации.

## Предметная область и владение

Admin Panel владеет собственными данными и бизнес-правилами для:

- центрального брендинга;
- конфигурации в области ответственности Admin Panel;
- центрального каталога;
- интеграционных контрактов, которыми управляет Admin Panel.

Центральная аутентификация на `7701` -- внешняя система, отвечающая только за identity и roles. Не переносите в Admin Panel владение учётными записями, паролями, сессиями или глобальными ролями. Сведения других систем не следует изменять напрямую: интеграция должна идти через согласованный и версионируемый контракт.

Будущие локальные порты: `7771` -- API, `7772` -- UI, `7773` -- PostgreSQL. Это резервирование, а не существующая конфигурация.

## Документация и решения

- Документация ведётся на русском языке, кроме текста стандартных лицензий, идентификаторов, имён протоколов и дословных внешних форматов.
- Каждый реализуемый объём работ начинается с плана в `docs/plans/`; планы являются частью репозитория и коммитятся вместе с изменениями.
- Существенные решения о границах сервисов, данных, auth, контрактах, версиях, хранилище и развёртывании фиксируйте в ADR и добавляйте в `docs/ADR_INDEX.md`.
- Перед разработкой страниц подготовьте описание сценариев, ролей, состояний и источников данных; UI не создаётся без явного утверждения пользователем.
- README и CHANGELOG обновляйте, когда меняется реальное состояние проекта или публичные договорённости.

## Конвенции для будущей реализации

- Сначала определяйте контракт, авторизацию и валидацию на серверной границе; затем реализуйте UI.
- Данные Admin Panel хранятся и изменяются только через его собственный прикладной слой. Не используйте общий доступ к БД других систем.
- Публичные и межсервисные контракты должны быть явными, версионируемыми и обратно совместимыми либо иметь согласованный путь миграции.
- Имена, форматирование, структура модулей, команды сборки и линтеры выбираются только после их документирования в утверждённом плане/ADR. Не создавайте «временный» стек без решения.
- Изменения держите узкими: не смешивайте документацию, инфраструктуру, доменную модель и UI в одной не связанной задаче.

## Тесты и проверка

При появлении кода каждое изменение должно иметь подходящую проверку:

- модульные тесты для доменных правил, валидации и преобразований;
- интеграционные тесты для собственного хранилища, API и контрактов;
- проверки авторизации для ролей, полученных от central auth;
- контрактные тесты для внешних интеграций и совместимости версий;
- E2E/браузерные проверки утверждённых пользовательских сценариев, включая ошибки, пустые состояния и узкий экран.

До выбора стека не выдумывайте команды тестирования. В реализации документируйте фактические команды и запускайте релевантные проверки до передачи работы.

## Секреты и безопасность

- Никогда не коммитьте пароли, токены, cookies, приватные ключи, реальные дампы, персональные данные или значения из production/stage.
- Не включайте секреты в документацию, примеры, логи, снимки экрана, тестовые фикстуры или сообщения об ошибках.
- Используйте переменные окружения и утверждённое хранилище секретов; шаблоны содержат только безопасные имена переменных.
- Уязвимости не публикуйте в issue или changelog: соблюдайте [SECURITY.md](SECURITY.md).

## Git-гигиена

- Перед работой проверяйте `git status`; не отменяйте чужие изменения.
- Не добавляйте сгенерированные файлы, локальные артефакты, зависимости или конфигурацию среды без явной необходимости.
- Не коммитьте и не публикуйте изменения без прямого поручения.
