# Техническое задание: SDLC Admin Panel

## 1. Назначение

`admin-panel` — независимая панель администрирования платформы SDLC. Она задает ограниченный набор общеплатформенных настроек и ведет реестр интеграций приложений. Панель не является прокси, API gateway, оркестратором процессов или заменой предметных настроек отдельных продуктов.

Первая поставка должна дать операторам единую точку для:

- просмотра и безопасного подключения приложений SDLC через реестр сервисов;
- управления центральной runtime-конфигурацией бренда;
- контроля статуса и совместимости зарегистрированных интеграций;
- аудита административных изменений.

## 2. Контекст и границы

| Компонент | Владение | Ответственность |
|---|---|---|
| Admin Panel | `admin-panel` | Реестр сервисов, центральная конфигурация бренда, роли панели, аудит, собственные API и UI. |
| Центральный auth | существующий сервис на `7701` | Выпуск идентичностей и ES256 JWT, публикация JWKS. Не хранит и не обслуживает настройки Admin Panel. |
| Потребитель бренда | каждое SDLC-приложение | Собственные безопасные дефолты, запрос и применение runtime-конфигурации, собственный UI. |
| Интегрируемый сервис | CI-CD, task-tracker, wiki, fleet-control и будущие сервисы | Свой предметный API, данные, учетные записи, секреты, endpoint интеграции и декларация capabilities. |

### 2.1. Что Admin Panel делает

- Хранит канонический реестр разрешенных сервисных интеграций.
- Принимает декларацию интеграции от сервиса и требует ее явного одобрения оператором до активации.
- Хранит общеплатформенную бренд-конфигурацию и выдает ее потребителям как runtime-документ.
- Проверяет доступность и совместимость только через заранее объявленные capabilities и endpoint интеграции.
- Ведет неизменяемый аудит административных действий.

### 2.2. Что Admin Panel не делает в v1

- Не хранит пользователей, пароли, сессии, refresh-токены или ключи центрального auth.
- Не использует storage auth-сервера и не пишет в него.
- Не проксирует запросы пользователей к SDLC-приложениям и не является API gateway/CDN.
- Не выполняет произвольные HTTP-вызовы, shell-команды, деплои, миграции либо удаленное управление сервисами.
- Не редактирует предметные данные: pipeline, задачи, wiki-документы, агенты, workflow и их локальные настройки.
- Не хранит секреты сервисов и не возвращает их в API, UI, логи или аудит.

## 3. Пользователи и доступ

| Роль | Права |
|---|---|
| `platform_viewer` | Просмотр активных сервисов, состояния интеграций, бренда и доступного ему аудита. |
| `platform_operator` | Подготовка изменений реестра и бренда; выполнение безопасной проверки интеграции. |
| `platform_admin` | Одобрение/отключение интеграций, публикация бренда, настройка ролей панели, просмотр полного аудита. |

Роли определяются из claims центрального JWT. Если claim не соответствует разрешенной роли, доступ к административному API запрещается. Сервис не создает локальных пользователей и не расширяет права токена.

## 4. Реестр сервисов

### 4.1. Модель регистрации

Сервис объявляет интеграцию декларацией, содержащей стабильный `service_key`, endpoint интеграции, версию контракта и ограниченный список capabilities. Endpoint и capabilities принадлежат самому сервису: Admin Panel не угадывает их и не конструирует удаленные URL.

Admin Panel хранит декларацию и свой операторский статус (`pending`, `active`, `disabled`, `retired`). Новый или измененный endpoint/capabilities требуют повторного одобрения. До одобрения запись не считается активной и не используется для проверок.

Начальный целевой набор ключей: `cicd`, `task-tracker`, `wiki`, `fleet-control`. `project-workflow` и `java-agent` допускаются только после регистрации; их отсутствие не является ошибкой v1.

### 4.2. Ограничения capability

Capabilities описывают только разрешенные контрактом операции наблюдения или выдачи настроек, например `health.read`, `integration.status.read`, `branding.runtime.read`.

В v1 запрещены capabilities, означающие произвольное удаленное выполнение, изменение предметных данных, доступ к файловой системе, выдачу секретов или универсальный webhook. Каждая capability должна быть известна каталогу Admin Panel; неизвестная capability отклоняется.

### 4.3. Состояния

| Состояние | Значение |
|---|---|
| `pending` | Декларация принята, но оператор еще не одобрил ее. |
| `active` | Декларация одобрена и доступна только в пределах утвержденных capabilities. |
| `disabled` | Интеграция временно запрещена; сервис и его данные не изменяются. |
| `retired` | Интеграция выведена из эксплуатации; история и аудит сохраняются. |

## 5. Центральный брендинг

### 5.1. Объект конфигурации

Admin Panel владеет единственным опубликованным документом `platform-branding`. В v1 он содержит только безопасные presentation-поля:

- `product_name`;
- `product_short_name`;
- `logo_url` и `favicon_url` (только разрешенные HTTPS URL либо относительные пути);
- `support_url`;
- `primary_color`, `accent_color` и `surface_color` в строгом формате цвета;
- `updated_at` и монотонную `revision`.

Конфигурация не содержит HTML, JavaScript, CSS произвольного содержания, учетные данные, токены, внутренние адреса и сервисные секреты.

### 5.2. Правило потребителя

Каждое приложение-потребитель обязано иметь встроенные безопасные дефолты. При первом запуске, сбое сети, `404`, недопустимом документе или устаревшем кеше приложение продолжает работать со своими дефолтами. Центральный брендинг улучшает представление, но не должен блокировать загрузку, аутентификацию или основной сценарий приложения.

### 5.3. Доставка v1

Потребитель запрашивает конфигурацию напрямую у API Admin Panel по HTTPS. Кеширование: короткий TTL `max-age=60`, revalidation через ETag и `If-None-Match`; ответ `304` сохраняет предыдущий валидный документ. В v1 нет CDN, reverse-proxy/gateway-слоя для бренда, push-канала, WebSocket и фоновой репликации.

## 6. План страниц до UI-кода

До создания UI-кода на каждую страницу обязателен отдельный текстовый сценарий, wireframe и явное согласование. Нельзя начинать реализацию страницы по одному названию маршрута.

| Приоритет | Страница | Цель | Основные данные и действия |
|---|---|---|---|
| P0 | `/login` | Вход через центральный auth | Редирект/экран ошибки без локальной формы пароля. |
| P0 | `/` | Обзор платформы | Счетчики активных/проблемных интеграций, текущая ревизия бренда, последние аудит-события. |
| P0 | `/services` | Реестр сервисов | Фильтр по состоянию, ключ, владелец, версия декларации, последнее безопасное состояние. |
| P0 | `/services/:serviceKey` | Карточка интеграции | Декларация, capabilities, операторский статус, история проверок и аудита; действия только из allowlist. |
| P0 | `/branding` | Черновик и публикация бренда | Валидация полей, preview, ETag/revision, публикация и rollback через новую ревизию. |
| P0 | `/audit` | Просмотр административного следа | Неизменяемый список действий с фильтрами времени, актора и сущности. |
| P1 | `/access` | Матрица доступа панели | Роли, сопоставление JWT claims с ролями панели; без управления пользователями auth. |

Для каждой P0-страницы проектировщик обязан зафиксировать: цель, состояние загрузки/пустого списка/ошибки/403, мобильный вариант, источник данных, разрешенные действия, confirmation для mutation и критерии e2e-проверки.

## 7. Функциональные требования v1

1. API доступен на порту `7771`, web-приложение — на `7772`, PostgreSQL — на `7773` в составе umbrella-развертывания.
2. Защищенные endpoints валидируют ES256 access JWT по JWKS центрального auth на `7701`; Admin Panel не принимает HMAC-режим и не выпускает токены.
3. Реестр валидирует уникальность `service_key`, разрешенную схему endpoint, версию декларации и allowlist capabilities.
4. Endpoint интеграции проверяется только согласованными read-only операциями; результат не меняет удаленный сервис.
5. Публикация бренда создает новую revision и новый ETag; опубликованный документ доступен потребителям без пользовательского JWT, если публикация не ограничена политикой развертывания.
6. Все мутации реестра, бренда, ролей и статуса интеграции создают audit event.
7. API возвращает структурированные ошибки, не раскрывающие секреты, внутренние topology-детали и ответы удаленных сервисов целиком.

## 8. Нефункциональные требования

- Production: HTTPS, строгий CORS allowlist, secure headers, параметризованные запросы, non-root runtime.
- P95 для чтения публичного бренда — до 200 мс без внешнего вызова; endpoint читает только локальную БД/кеш процесса.
- Сервис устойчив к временному отказу auth JWKS после ранее успешного получения ключей в пределах безопасного кеша; при отсутствии валидного ключа защищенные операции запрещены.
- Интеграционные проверки имеют жесткие timeout, ограничение размера ответа, denylist private/link-local адресов и не следуют произвольным redirect.
- Документация, OpenAPI и миграции обновляются вместе с изменением контракта или модели.

## 9. Критерии приемки первой реализации

- Реализованный набор страниц соответствует утвержденному плану страниц и wireframes.
- Нельзя активировать сервис без валидной декларации и одобрения администратора.
- Нельзя вызвать неописанную capability или передать произвольный URL для удаленного вызова.
- Потребитель получает `200` с ETag, затем `304` по `If-None-Match`; при недоступности Admin Panel работает со своим дефолтом.
- JWT с неподходящим алгоритмом, issuer, audience, истекшим временем или неизвестным `kid` не дает административный доступ.
- В API, документации, примерах, логах и миграциях нет значений секретов.
