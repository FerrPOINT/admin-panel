# Кеширование runtime-конфигурации

## Цель

Product frontends получают опубликованную runtime-конфигурацию напрямую из API Admin Panel. Кеширование уменьшает нагрузку и не делает Admin Panel единственной точкой отказа: каждый продукт сохраняет встроенные defaults и использует их, если конфигурация недоступна или невалидна.

В v1 не используются CDN и API gateway. Политика применяется на уровне API-клиента продукта и HTTP-ответов API `7771`.

## Объект кеширования

Кешируется только опубликованная конфигурация для определенной области/потребителя и версии runtime-контракта. Не кешируются черновики, аудит, права, диагностические детали соединений или ответы с ошибкой авторизации.

Пример ключа:

```text
runtime-config:{contractVersion}:{scope}:{consumer}
```

Ключ не содержит токенов, персональных идентификаторов и секретных значений.

## HTTP-контракт

- Успешный ответ содержит тело конфигурации, `ETag`, `Cache-Control` и версию контракта.
- Клиент хранит последний проверенный ETag и отправляет `If-None-Match` после истечения TTL или при явной проверке.
- При совпадении API возвращает `304 Not Modified` без тела; клиент продлевает локальную свежесть.
- После успешной публикации генерируется новый ETag. ETag строится из неизменяемой опубликованной версии/содержимого, а не из времени ответа.
- `Cache-Control` в v1 ограничивает shared caching, например `private, max-age=<TTL>, must-revalidate`, пока не появится отдельно спроектированный edge-контур.

Точные TTL и лимиты утверждаются с продуктами до реализации. Начальная политика должна быть консервативной: достаточно короткий TTL для операционных изменений и достаточно длинный, чтобы выдерживать краткие сбои API. Значение не фиксируется в этом документе как production-конфигурация.

## Алгоритм клиента

1. При старте загрузить последний валидный локально сохраненный runtime snapshot, иначе встроенные defaults продукта.
2. Если snapshot свежий, использовать его и планировать проверку по TTL.
3. При проверке отправить `If-None-Match` с последним ETag.
4. При `200` валидировать схему и атомарно сохранить новый snapshot с ETag и временем проверки.
5. При `304` обновить только время проверки.
6. При timeout, `5xx`, ошибке схемы или сети продолжить с последним валидным snapshot; если его нет - со встроенными defaults.
7. Не удалять рабочий snapshot из-за единичной ошибки получения.

## Инвалидация

Публикация является единственным штатным источником инвалидации: новая версия меняет ETag. Продукты не получают push-инвалидацию в v1; максимальная задержка применения определяется TTL и следующей проверкой. При критическом изменении оператор может сократить TTL только через утвержденную политику или инициировать предусмотренную продуктом принудительную проверку, не меняя старую конфигурацию задним числом.

## Безопасность и целостность

- Перед кешированием клиент валидирует типы, версию схемы и allowlist полей.
- В конфигурации нет секретов; все же локальное хранилище должно защищаться согласно политике продукта.
- Нельзя смешивать конфигурации разных consumer/scope.
- Устаревший snapshot остается допустимым только в пределах явно определенного максимального возраста; после него продукт безопасно использует embedded defaults и отправляет наблюдаемый сигнал.
- Нельзя принимать ответ, полученный без ожидаемой аутентификации/проверки происхождения, если endpoint требует ее.

## Наблюдаемость

Фиксируются и агрегируются: cache hit/miss, `200`/`304`, возраст snapshot, ETag-версия, ошибка валидации, fallback на cached snapshot/defaults. Нельзя записывать в метрики или логи весь объект конфигурации, если он может содержать чувствительные бизнес-параметры.

## Проверки

Должны быть автоматизированы сценарии: первый запуск без кеша, `200` и сохранение, `304`, новая ETag после публикации, поврежденный кеш, недоступный API, превышение max stale age, разделение ключей разных потребителей и запрет доступа к черновику.
