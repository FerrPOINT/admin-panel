# Runtime Inspector: корректная повторная проверка

## Сценарии

- После успешной загрузки ошибка сети или невалидный ответ каталога показывают ошибку и скрывают прежние строки и список возможностей. Повторный запрос сохраняет проверенный ETag и может восстановить тот же снимок по `304`.
- ETag обновляется только после проверки тела ответа; невалидный JSON не становится новой кешированной версией. `304` без проверенного локального снимка является ошибкой, а не пустым каталогом или отсутствием брендинга.
- Пустой валидный каталог остаётся отдельным состоянием; его `304` сохраняет пустое состояние. Предыдущий брендинг при обновлении или ошибке остаётся доступен для диагностики с явной пометкой.
- Контракт `/api/v1/runtime/*` не меняется; источник данных по-прежнему Admin Panel.

## Проверки

- Unit: успешный каталог, затем 500/невалидный ответ, отсутствие старых строк, retry с `304` и восстановление; `304` без снимка и пустой валидный каталог.
- Unit: невалидный брендинг не меняет ETag, `304` без снимка показывает ошибку; ранее проверенный брендинг явно отмечен как предыдущий при обновлении.
- Lint, typecheck, unit и production build в CI; live браузерная проверка после освобождения места на рабочем стенде.
