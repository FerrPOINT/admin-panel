# Надёжная публикация брендинга

## Сценарий и источник данных

Авторизованный пользователь меняет брендинг в `/branding` и нажимает
«Опубликовать». Admin API сначала создаёт неизменяемую draft-ревизию через
`POST /api/v1/branding/revisions`, затем публикует её через
`POST /api/v1/branding/revisions/{revision}/publish`. Список ревизий Admin API
остаётся источником текущей опубликованной конфигурации. Права и API-контракт
не меняются.

## Состояния

- Пока создание или публикация выполняется, кнопка и все поля формы недоступны;
  отправляется снимок данных на момент нажатия.
- Ошибка создания сохраняет редактируемый черновик формы; повторная попытка
  начинает создание заново.
- Если создание удалось, но публикация не прошла, номер созданной ревизии
  сохраняется в состоянии страницы. Повторная попытка публикует эту же
  ревизию, не создавая дубликат. Поля остаются видимыми, но заблокированы.
- Пользователь может явно вернуться к редактированию. Прежний черновик
  остаётся в истории, а следующая попытка создаёт новую ревизию; интерфейс
  сообщает об этом до отправки.
- Успех показывается только после подтверждения публикации. После изменения
  любого поля прежнее сообщение об успехе исчезает.

## Проверка и выпуск

Unit-тесты покрывают ошибку создания, ошибку публикации и повтор той же
ревизии, блокировку обеих стадий, начало новой ревизии после изменения и
сброс сообщения об успехе. Запустить полный frontend test, typecheck,
обычный и semantic lint, production build в CI. Финальный gate: no-mock
публикация на живом QA-стенде с отдельной тестовой ревизией, проверка
ошибки/retry, узкого экрана, клавиатуры и трёх тем. Рабочие volumes не
сбрасывать.
