# API Versioning

## 1. Политика

Публичный API Admin Panel использует явную major-версию в URL: `/api/v1/...`. Версия описывает HTTP-контракт, включая ресурсы, поля, семантику и ошибки. Текущая v1 поддерживается до объявленного срока снятия; версия не меняется из-за внутреннего refactoring.

## 2. Совместимые изменения в v1

Без новой major-версии допустимы:

- новый необязательный endpoint, поле ответа или capability;
- новое необязательное поле запроса с безопасным default;
- расширение allowlist значений, когда старый клиент корректно его игнорирует;
- исправление ошибки, если не меняется документированная семантика.

Клиент обязан игнорировать неизвестные поля ответа и не предполагать порядок полей JSON. Сервер обязан сохранять документированные defaults и семантику существующих полей.

## 3. Несовместимые изменения

Новая major-версия обязательна для удаления/переименования поля или endpoint, смены типа/семантики поля, изменения аутентификации, ужесточения ранее разрешённой capability и изменения error contract, на который клиент мог опираться. Новая версия живёт параллельно со старой в период миграции.

Для каждой deprecation публикуются: замена, срок поддержки, миграционный пример без секретов и метрики использования. Удаление проводится после срока и подтверждения, что активные зарегистрированные consumers мигрировали или имеют согласованное исключение.

## 4. Configuration и capability contracts

Схема runtime config versioned отдельно от URL API: payload содержит `schema_version` и устойчивый `revision_id`. Consumer валидирует известную schema и применяет собственные безопасные defaults к отсутствующим необязательным полям. Неизвестная обязательная capability или неподдерживаемая major schema не активирует новый режим: consumer сохраняет безопасную конфигурацию и сообщает диагностическое состояние.

Capability имеет стабильное имя и версионируемую schema. Её удаление или смена значения, приводящая к более широкому доступу/контролю, несовместима и требует новой capability либо согласованной major migration.

## 5. Заголовки и cache validators

`ETag` относится к конкретному представлению revision/runtime config. `If-None-Match` оптимизирует чтение, `If-Match` защищает запись. ETag нельзя трактовать как номер API-версии или как permission grant.

## 6. OpenAPI

OpenAPI-артефакт фиксирует версию и собирается из backend DTO. В CI сравнивается с предыдущим опубликованным контрактом. Неожиданный breaking change блокирует релиз, пока не добавлены новая major-версия и план миграции либо не исправлена регрессия.
