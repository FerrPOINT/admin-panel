# Code Style

## 1. Общие правила

- Язык документации, сообщений UI и описаний ошибок -- русский; идентификаторы, имена типов, полей API и комментарии в коде -- английский.
- Изменение поведения сопровождается изменением тестов и относящейся к нему документации в том же pull request.
- Предпочтительны небольшие, явно названные модули и функции; абстракция добавляется только при наличии повторяющегося поведения.
- Не допускаются секреты, access token, персональные данные и полные конфигурационные снимки в коде, тестовых фикстурах, логах или документации.

## 2. Backend Rust

- Используется актуальная stable Rust edition 2024, `rustfmt` и `clippy`; обязательны `cargo fmt --all -- --check` и `cargo clippy --workspace --all-targets -- -D warnings`.
- Границы слоёв: `api -> application -> domain -> infrastructure`. HTTP handler переводит transport DTO в команду/запрос приложения и не содержит SQL или правил предметной области.
- Общие зависимости передаются через явный `AppContext`; глобальное изменяемое состояние запрещено.
- Публичные структуры запросов и ответов отделены от persistence-моделей. Ошибки домена преобразуются в единый API-envelope на HTTP-границе.
- Входные данные валидируются до изменения состояния. Операции конфигурации требуют явной авторизации и формируют audit event.
- Асинхронный код не должен удерживать транзакцию, mutex или подключение к БД во время сетевого вызова.

## 3. Frontend TypeScript

- TypeScript работает в strict-режиме; `any`, небезопасные assertions и неявные runtime-конфигурации запрещены.
- Сгенерированные OpenAPI-типы и клиент не редактируются вручную. UI не дублирует DTO собственными несовместимыми типами.
- Серверное состояние живёт в TanStack Query; локальное UI-состояние -- в компоненте или узком Zustand store. Конфигурация сервера не кэшируется как постоянная клиентская истина.
- Компонент получает данные и callbacks через типизированные props. Сетевые вызовы и преобразование transport DTO не размещаются в презентационных компонентах.
- Формы используют схему валидации, доступную пользователю ошибку поля и явно обрабатывают конфликт/устаревшую конфигурацию.

## 4. Именование и форматирование

- Rust: `snake_case` для модулей, функций и полей; `PascalCase` для типов и trait; булевы значения начинаются с `is_`, `has_`, `can_` или `should_`.
- TypeScript: `camelCase` для значений и функций, `PascalCase` для компонентов и типов; имена файлов соответствуют локальной конвенции слоя.
- HTTP JSON использует `snake_case`; UI может адаптировать только в едином API-клиенте.
- Время передаётся и хранится как ISO 8601 в UTC. Деньги, лимиты и длительности не передаются неразмеченными строками.

## 5. Проверка

Перед merge обязательны форматирование, линтеры, релевантные unit/integration тесты, проверка OpenAPI-совместимости и frontend build. Для изменённого административного сценария требуется браузерная проверка успешного, пустого, ошибочного и запрещённого состояния.
