# Устойчивость

## Модель отказов

Admin Panel зависит от PostgreSQL, central auth `7701` и зарегистрированных health endpoints интеграций. Product frontends не должны зависеть от доступности Admin Panel для базовой работы: их защита - embedded defaults и последний валидный runtime snapshot.

## Цели v1

- Не публиковать частичную или невалидную конфигурацию.
- Не допускать каскадную перегрузку от медленных интеграций.
- Сохранять аудит и воспроизводимость изменений при повторе запросов.
- Давать операторам точное различие между недоступностью Admin Panel, auth, БД и внешней интеграции.

## Защита API и БД

- Разделить liveness и readiness: живой процесс не означает доступную БД/авторизацию.
- Использовать ограниченный pool БД, тайм-аут ожидания соединения и backpressure при исчерпании.
- Публикацию выполнять в короткой транзакции с оптимистичным контролем базовой версии.
- Ввести idempotency key для повторяемых изменяющих запросов, прежде всего публикации.
- Ограничить размер тела, сложность фильтров и частоту дорогостоящих операций.
- При миграции применять expand/migrate/contract, чтобы несколько версий приложения могли сосуществовать во время rollout.

## Защита интеграций

Для зарегистрированной health-проверки устанавливаются отдельные connect/read/overall timeout, ограничение одновременных проверок на сервис и глобальный бюджет. Повтор допускается только для временных сетевых/5xx-ошибок, с exponential backoff, jitter и малым числом попыток. `4xx`, ошибка схемы и запрет policy не повторяются автоматически.

Circuit breaker имеет состояния closed, open и half-open. При серии сбоев endpoint временно не вызывается, UI показывает последний результат и время следующей разрешенной проверки. В half-open разрешается ограниченное число проб. Проверка не выполняет произвольные endpoint и не тянет доменные данные сервиса.

## Деградация по зависимостям

| Отказ | Поведение |
| --- | --- |
| PostgreSQL недоступен | readiness = false; изменяющие операции отклоняются; API не выдает сомнительные данные как свежие |
| Central auth недоступен | новые защищенные сессии не обслуживаются по fail-open; существующая проверка действует только в пределах безопасной политики токена |
| Health endpoint интеграции недоступен | сервис получает `Error`/`Warning`; публикация блокируется только если зависимость обязательна для изменяемого capability |
| Runtime API Admin Panel недоступен | product frontend использует кеш или embedded defaults |
| Frontend `7772` недоступен | runtime API `7771` и продуктовые клиенты не должны зависеть от UI |

## Данные и восстановление

Версии конфигурации и аудит являются append-only с точки зрения прикладного контракта. Backup PostgreSQL регулярно проверяется тестовым восстановлением. RPO/RTO и частота backup согласуются до production; без доказанного восстановления нельзя считать резервирование завершенным. Точки восстановления связываются с версией схемы и релизом.

## Поведение клиента runtime API

Клиент не перезаписывает последний валидный snapshot ошибочным ответом. После max stale age он переходит на embedded defaults и фиксирует наблюдаемый сигнал. Устаревшая конфигурация не должна бесконечно удерживать отключенную по безопасности интеграцию: для таких полей контракт предусматривает безопасные default-значения на стороне продукта.

## Проверка устойчивости

Проводятся controlled fault scenarios: остановка/задержка БД, timeout/DNS failure health endpoint, `429` и `5xx` auth adapter, одновременная публикация, повтор запроса после потери ответа, поврежденный runtime snapshot и рестарт приложения во время проверки. Критерий: нет потери опубликованной версии, нет утечки секрета, нет неконтролируемого retry storm, а причина доступна по correlation ID.
