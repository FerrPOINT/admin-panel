# Тестирование

## Цели качества

Тестирование подтверждает, что Admin Panel безопасно управляет только своей конфигурацией и реестром интеграций, не раскрывает секреты, не выполняет произвольные удаленные операции и сохраняет воспроизводимую историю публикаций.

## Пирамида проверок

| Уровень | Что проверяем | Примеры |
| --- | --- | --- |
| Unit | Чистая бизнес-логика | валидация capability, diff версий, ETag, маскирование чувствительных полей |
| Integration | API, PostgreSQL, central auth adapter | роли, миграции, транзакционная публикация, audit trail |
| Contract | Runtime API для продуктов | схема ответа, `ETag`, `If-None-Match`, `304`, TTL |
| E2E | Утвержденные UI-сценарии | черновик брендинга, публикация, каталог, диагностика |
| Non-functional | Нагрузка и отказы | деградация БД, timeout интеграции, concurrent publish |

## Обязательные сценарии

### Доступ и аудит

- Неавторизованный запрос получает безопасный отказ без деталей внутренней системы.
- Reader не может изменить, publisher не может управлять каталогом без нужной роли, administrator не получает прав central auth администратора автоматически.
- Все изменения и публикации содержат автора, время, объект, причину и correlation ID.
- Аудит неизменяем: API не предоставляет обновление или удаление аудиторской записи.

### Брендинг и конфигурации

- Черновик сохраняется без воздействия на опубликованную версию.
- Публикация проверяет схему, обязательную причину и права publisher.
- Публикация атомарна: при ошибке нет частично опубликованного состояния.
- Откат создает новую опубликованную версию с прежним содержимым и отдельной записью аудита.
- Попытка передать ключ, токен, пароль или аналогичный секрет отклоняется и не попадает в лог.
- Параллельная публикация не теряет изменения: используется конфликт версий или оптимистичная блокировка.

### Каталог и интеграции

- В endpoint допускаются только разрешенные метод, путь и схема хоста согласно политике реестра.
- Нельзя создать возможность, не связанную с сервисом, или дважды назначить один и тот же endpoint.
- Экран и API не предлагают чтение/изменение удаленных доменных сущностей.
- Ручная проверка вызывает только зарегистрированный health endpoint с заданным тайм-аутом.
- Ошибки внешнего сервиса не возвращают пользователю секреты, заголовки авторизации или полные ответы upstream.

### Runtime API и кеш

- Опубликованная конфигурация возвращает стабильный ETag.
- Запрос с совпадающим `If-None-Match` возвращает `304` без тела.
- После публикации ETag изменяется; устаревший клиент получает новую конфигурацию при следующей проверке TTL.
- При недоступности runtime API продукт использует встроенные defaults, а не пустую конфигурацию.
- Неопубликованный черновик никогда не доступен потребителям runtime API.

### UI после согласования

- Для каждой страницы из `UI_UX.md` проверяются loading, empty, error, forbidden и stale состояния.
- Публикация требует подтверждения и показывает diff.
- Неразрешенные кнопки не выполняют запрос при обходе интерфейса: сервер повторно проверяет роль.
- На мобильной ширине навигация и таблицы остаются пригодными для работы.
- E2E запускается только после отдельного явного согласования wireframes и реализованного UI.

## Тестовые данные

Используются изолированные PostgreSQL-базы/схемы и фикстуры без реальных токенов, персональных данных и production URL. В фикстурах нужны: одна опубликованная и одна черновая версия, сервисы с `OK`, `Warning`, `Error`, пользователи всех ролей и контролируемая имитация central auth.

## Команды и контроль качества

Фактические команды определяются после выбора стека. Минимальный pipeline: форматирование и статический анализ, unit, integration с PostgreSQL, contract runtime API, E2E утвержденных экранов, проверка миграции на чистой и обновляемой базе. Сборка или релиз не допускаются при провале любой обязательной группы.

## Критерии приемки

- Все обязательные тесты проходят воспроизводимо в чистом окружении.
- Миграции применяются и откатываются в тестовом сценарии согласно политике БД.
- Есть доказательство conditional GET и fallback на product defaults.
- Есть доказательство запрета секретов и произвольных remote CRUD-операций.
- После UI-реализации есть E2E-доказательства для всех утвержденных страниц.
