# Развертывание

## Топология v1

Admin Panel разворачивается как три компонента с внутренней связью:

| Компонент | Порт | Назначение |
| --- | ---: | --- |
| API | `7771` | Admin API, runtime API, аудит, проверки соединений |
| Frontend | `7772` | Веб-интерфейс администрирования |
| PostgreSQL | `7773` | Собственные данные панели: реестр, версии, аудит, статусы |
| Central auth | `7701` | Внешняя зависимость для identity и ролей |

Frontend обращается к API Admin Panel; API обращается к PostgreSQL и проверяет identity/roles через central auth. Product frontends запрашивают runtime-конфигурацию напрямую у API `7771`. В v1 нет CDN и gateway.

## Предварительные условия

- Выделенные DNS-имена и TLS для frontend/API.
- PostgreSQL доступен только из доверенной сети приложения и контура резервного копирования.
- Подтвержденная интеграция с central auth `7701`.
- Секреты приложения находятся во внешнем защищенном хранилище/переменных окружения, но не в БД конфигураций и не в runtime API.
- Подготовлены резервная копия БД и проверенная процедура восстановления.

## Порядок релиза

1. Проверить артефакты, SBOM/зависимости и результаты обязательных тестов.
2. Создать проверяемый backup PostgreSQL и зафиксировать его идентификатор в релизной записи.
3. Применить миграции как отдельный контролируемый шаг; при сбое остановить релиз.
4. Развернуть API, дождаться readiness и проверить подключение к БД и central auth.
5. Развернуть frontend, проверить доступность и CSP/HTTPS.
6. Выполнить smoke-сценарии: вход с ролью reader, просмотр опубликованной конфигурации, conditional GET, просмотр здоровья.
7. Включить трафик к новой версии и наблюдать ошибки, latency, доступность БД и auth в заданное окно.

## Миграции и rollback

Миграция обязана быть версионирована, идемпотентна в рамках выбранного инструмента и протестирована на копии production-схемы. Деструктивные изменения выполняются по схеме expand/migrate/contract: сначала обратносуместимое расширение, затем перенос, а удаление - в отдельном релизе.

Rollback приложения не должен автоматически откатывать БД, если это опасно для данных. При проблеме после миграции: остановить публикации, вернуть совместимую версию приложения, восстановить БД только по решению оператора и проверенному runbook. Откат конфигурации выполняется публикацией новой версии, а не изменением старой.

## Post-deploy проверка

- `/health/live` подтверждает живой процесс, `/health/ready` - готовность зависимостей.
- API `7771` отдает опубликованную runtime-конфигурацию, ETag и корректный `304`.
- UI `7772` доступен авторизованному пользователю и не раскрывает запрещенные действия.
- В БД есть ожидаемая версия схемы; аудит доступен.
- Состояние интеграций не ухудшилось из-за релиза; любые проверки ограничены политикой нагрузки.

## Безопасность эксплуатации

Не логировать `Authorization`, cookie, токены, пароли, тела потенциально чувствительных ответов. Ограничить CORS доверенными origins frontend/product frontend. Использовать TLS, минимальные DB-права, ротацию учетных данных инфраструктуры и отдельный service account для миграций. Доступ к журналам и backup должен быть ограничен так же строго, как доступ к базе.

## Остановка релиза

Релиз останавливается при любой из ситуаций: неприменимая миграция, readiness не достигнут, рост 5xx/ошибок авторизации выше порога, runtime API возвращает неполную конфигурацию, выявлена утечка секрета или нарушена неизменяемость аудита. Решение и correlation ID фиксируются в операционном журнале.
