# ADR-0008: Управление пользователями через Central Auth

## Status

Accepted

## Context

Пользователю нужна единая страница управления учётными записями и личными
API-токенами, но владельцем identity, credentials, browser sessions и token
lifecycle является Central Auth. Прямой доступ Admin Panel к его базе данных
нарушил бы границы сервисов и усложнил аудит и отзыв секретов.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| Копировать пользователей в Admin Panel | независимое чтение | два источника истины, рассинхронизация статусов |
| Подключить базу Central Auth напрямую | мало HTTP-кода | жёсткая связь схем и обход политики сервиса |
| Проксировать Central Auth API | единый lifecycle и валидация | доступность операций зависит от Central Auth |

## Decision

Admin Panel предоставляет UI и тонкий HTTP proxy к версионированному API
Central Auth. Bearer-токен пользователя передаётся только в заголовке. Ответы
управления не кэшируются. Admin Panel записывает локальный audit успешных
изменений, используя проверенный центральный `sub`, но не сохраняет пароль,
setup-link, browser session, личный token secret или копию user directory.

Для вошедших людей локальные role bindings не влияют на доступ: любой валидный
пользователь получает одинаковые возможности Admin Panel. Исторические поля и
endpoint role bindings сохраняются временно для совместимости, их UI скрыт.
Машинные токены и service scopes остаются отдельным механизмом.

## Consequences

- Central Auth остаётся единственным источником пользователей и секретов.
- Недоступность Central Auth приводит к явному `502/503`, без локального входа.
- Пользовательские изменения видны в центральном каталоге сразу после ответа.
- Любой вошедший пользователь может управлять платформой; это принятое
  продуктовое ограничение текущей модели без пользовательских ролей.
