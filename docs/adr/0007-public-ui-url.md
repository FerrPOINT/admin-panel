# ADR-0007: Публичный UI URL в декларациях сервисов

- Статус: Принят
- Дата: 2026-09-13

## Контекст

Каталог v1.1 (`GET /api/v1/runtime/services`) отдаёт `ui_url = integration_base_url`
декларации. `integration_base_url` — служебный адрес для health-проб и
межсервисных вызовов из контейнера админ-панели (loopback `http://localhost:<port>`).
За TLS-фасадом (`*.base.localhost:7743`, Caddyfile.umbrella) платформенный
переключатель сервисов уводит пользователя обратно на plain-HTTP loopback URL.

Рассматривались варианты:

1. Рерайт `ui_url` в каталоге по `X-Forwarded-Proto`/`Host` — хардкодит схему
   хостов фасада (`admin`, `forge`, `tracker`, …) в код каталога; каталог
   начинает знать о конкретном инсталле.
2. Отдельное поле `public_ui_url` в декларации — значение задаёт оператор
   инсталляции при регистрации (какой URL показывать пользователям), каталог
   отдаёт его прозрачно. Не задано → прежнее поведение (integration_base_url).

## Решение

Добавить в `service_declarations` колонку `public_ui_url TEXT NULL`
(миграция 0005; данные не бэкфиллятся — задаются новыми декларациями или
через API оператором инсталляции).

Каталог v1.2: `ui_url = public_ui_url ?? (ui.render ? integration_base_url : null)`.

Валидация на серверной границе: `public_ui_url` — опциональный `http(s)://` URL
без credentials; отклоняется иначе. `integration_base_url` продолжает
использоваться для health-проб без изменений.

## Альтернативы

- Хранить оба URL в branding-документе — нарушает владение: адреса сервисов
  принадлежат реестру, не бренд-конфигу.
- Не решать: TLS-инсталлы остаются со «съезжающим» переключателем.

## Последствия

- Декларации API (`POST /services/{key}/declarations`) принимают необязательный
  `public_ui_url`; существующие декларации без поля валидны (обратная совместимость).
- На HTTP-стенде ничего не меняется; на TLS-инсталле оператор указывает
  `https://<host>.base.localhost:7743`-адреса в декларациях.
- OpenAPI и docs/API.md §7.3 обновляются (v1.2).
