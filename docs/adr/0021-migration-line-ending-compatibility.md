# 0021. Совместимость checksum миграций LF/CRLF

Статус: принят. Дата: 2026-10-05.

## Контекст

SQLx использует SHA-384 исходного SQL. Windows checkout может записать CRLF,
а Linux checkout того же файла — LF. В действующем SDLC2 версии 1–6 и 8 имеют
CRLF-checksums; изменение файлов на LF блокирует старт до применения новых миграций.

## Решение

Модуль migration читает ledger и разрешает в памяти только вариант LF или CRLF
того же SQL, чей SHA-384 точно совпадает с ранее записанным checksum. Файлы и
ledger не меняются. Настройки locking, dirty/version checks и транзакции остаются
в SQLx. Новая установка использует обычный checksum текущего файла.

Любое отличие SQL, не объясняемое этими line endings, по-прежнему возвращает
VersionMismatch. Не включаются ignore-missing, skip-checksum или автоматическое
исправление ledger. Конкурентная миграция между чтением и SQLx lock может привести
к безопасному отказу старта; повторный старт читает уже подтверждённый ledger.

## Проверка

Unit test отклоняет изменённый SQL и произвольный checksum. PostgreSQL-тест на
отдельной БД admin_migration_test проверяет все десять миграций: исторические
CRLF→LF, новую установку LF→CRLF, неизменность ledger и отказ при изменении SQL.
Команда: `python scripts/test_ai_foundation.py`. Рабочие БД тест не принимает.

Совместимость опирается на публичные semver-exempt поля Migrator SQLx 0.8.6,
закреплённого lockfile; обновление SQLx требует повторить эту проверку.
