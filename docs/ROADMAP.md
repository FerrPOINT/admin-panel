# Roadmap

## Цель v1

Создать самостоятельный Admin Panel с собственными API и PostgreSQL для управления платформенным брендингом, реестром интеграций, публикуемыми конфигурациями и диагностикой. Продуктовые фронтенды получают только версионированную runtime-конфигурацию по прямому API с ETag и TTL-кешем. CDN и gateway в v1 не используются.

## Вне рамок v1

- CRUD доменных объектов удаленных сервисов.
- Хранение секретов и токенов в runtime-конфигурации.
- Замена central auth или управление учетными записями.
- CDN, API gateway и распределенный конфигурационный контур.
- Автоматическое исправление проблем внешних сервисов.

## Этап 0. Согласование продукта

Результат: утверждены границы, страницы, модель ролей и wireframes.

- Подтвердить `docs/UI_UX.md` явным решением пользователя.
- Зафиксировать набор потребителей runtime-конфигурации.
- Утвердить формат реестра сервисов: владелец, capability, allowlist endpoint, health-check.
- Согласовать правила публикации и отката.

Критерий выхода: пользователь явно одобрил wireframes; UI-код еще не написан.

## Этап 1. Каркас и авторизация

Результат: запускаемые API, frontend и PostgreSQL на планируемых портах `7771`, `7772`, `7773`.

- Интегрировать central auth `7701` только для идентификации и ролей.
- Ввести роли reader, editor, publisher, administrator.
- Настроить миграции и минимальную схему аудита.
- Реализовать health/readiness самого приложения.

Критерий выхода: авторизованный пользователь получает только разрешенные действия; сервисы проверяются локально.

## Этап 2. Реестр интеграций

Результат: управляемый каталог сервисов без удаленного CRUD.

- Реализовать сервисы, владельцев, статусы и документацию.
- Описать явные capabilities и разрешенные endpoints.
- Валидировать HTTP-метод, путь, тайм-ауты и уникальность capability.
- Добавить безопасный запуск зарегистрированной health-проверки.

Критерий выхода: нельзя сохранить произвольный URL, секрет или операцию с доменными данными внешнего сервиса.

## Этап 3. Конфигурации и публикация

Результат: черновики, неизменяемые версии, сравнение, публикация и откат.

- Хранить версии конфигурации и причину изменения.
- Проверять схему, запрет секретных полей и зависимые соединения.
- Публиковать атомарно с новым ETag.
- Отдавать runtime API для продуктовых фронтендов с `Cache-Control` и conditional GET.

Критерий выхода: фронтенд может использовать встроенные defaults при недоступности API и применить подтвержденную опубликованную конфигурацию при успехе.

## Этап 4. UX после одобрения

Результат: все утвержденные страницы из `docs/UI_UX.md`.

- Реализовать навигацию, обзор, брендинг, каталог, версии, аудит и здоровье.
- Добавить состояния загрузки, пустого списка, ошибки, запрета доступа и устаревших данных.
- Проверить desktop и узкий мобильный viewport.

Критерий выхода: UI создан только после явного одобрения wireframes и проверен реальным сценарием.

## Этап 5. Наблюдаемость и устойчивость

Результат: измеримая и деградирующая предсказуемо система.

- Добавить структурированные логи, метрики, трассировку и аудит.
- Ввести тайм-ауты, повторы с jitter, ограничения параллелизма и circuit breaker для проверок интеграций.
- Настроить алерты на ошибки публикации, устаревшие проверки и деградацию БД.
- Провести сценарии отказа зависимостей.

Критерий выхода: операторы видят причину сбоя по correlation ID и система не распространяет каскадную нагрузку.

## Этап 6. Подготовка к эксплуатации

Результат: повторяемый релиз и операционные инструкции.

- Выполнить тестовую миграцию и резервное копирование PostgreSQL.
- Проверить rollback приложения и конфигурации.
- Провести security review доступа, журналов и запрета секретов.
- Сформировать runbook для инцидентов и публикации.

Критерий выхода: релиз проходит checklist без ручного изменения производственных данных.

## Зависимости и решения

- Central auth `7701` должен предоставлять проверяемые идентичности и роли.
- Каждый продукт сохраняет собственные встроенные defaults; Admin Panel не становится единой точкой отказа для рендера продукта.
- Владелец каждой интеграции отвечает за контракт health endpoint и capability.
- Изменение runtime API должно быть обратно совместимо либо выпускаться новой версией контракта.
