# Наблюдаемость

## Цель

Наблюдаемость должна отвечать на вопросы: какая версия конфигурации опубликована, кто ее изменил, почему публикация не прошла, доступна ли БД/auth/интеграция, получают ли продукты свежую конфигурацию и где возникла ошибка. Она дополняет неизменяемый аудит, но не заменяет его.

## Идентификаторы и контекст

Каждый входящий запрос получает или принимает проверяемый `requestId`/correlation ID. Он передается в API-логи, audit event, вызовы health endpoint и trace context. Для публикации добавляются `draftId`, базовая/новая версия и actor ID. В логи не попадают секреты, cookie, `Authorization`, содержимое токена и полные чувствительные payload.

## Структурированные логи

Минимальные поля:

```text
timestamp, level, service, environment, requestId, traceId,
actorId_hash, operation, resourceType, resourceId, outcome,
httpStatus, latencyMs, errorCode
```

Для интеграций дополнительно: service registry ID, capability, endpoint ID, result class, timeout phase. URL логируется после нормализации и без query-параметров, если они потенциально чувствительны. `actorId_hash` применяется там, где прямой идентификатор не нужен для отладки; полный субъект хранится в защищенном audit trail согласно политике доступа.

## Метрики

### API и runtime-конфигурация

- частота запросов, ошибки `4xx`/`5xx`, latency p50/p95/p99;
- `200`/`304`, cache hit/miss, возраст последнего snapshot и fallback на defaults;
- число публикаций, конфликты версий, длительность валидации и транзакции;
- версии runtime-контракта и доля клиентов на каждой версии.

### Зависимости

- статус liveness/readiness;
- pool PostgreSQL: занятость, ожидание, ошибки, latency запросов;
- central auth: latency, коды ответов, ошибки валидации identity;
- health-check: успех/ошибка/timeout, latency, circuit breaker state, очереди и ограничение параллелизма.

### Безопасность и аудит

- неуспешные входы/проверки токенов, `403` по операциям, rate limit;
- отклоненные конфигурации с классификацией причины;
- попытки передать запрещенное секретное поле;
- отставание записи аудита, если аудит реализован через надежную outbox/очередь.

Метки метрик имеют низкую кардинальность: тип операции, код результата, сервисный ID, capability, окружение. Нельзя использовать request ID, пользовательский текст или произвольный URL как label.

## Трассировка

Трассировка охватывает: HTTP-запрос, авторизацию, запросы к БД, валидацию черновика, транзакцию публикации и безопасно описанный вызов health endpoint. Атрибуты трассы не содержат секреты или полные конфигурации. Trace ID отображается оператору через request ID/диагностическую ссылку, но не дает пользователю доступ к защищенным логам.

## Дашборды

1. `Состояние платформы`: API, frontend, БД, auth, readiness, релиз.
2. `Конфигурации`: публикации, конфликты, длительность, ошибки валидации, распространение ETag.
3. `Интеграции`: состояние endpoint, timeout, circuit breaker, история проблем.
4. `Безопасность`: отказанные доступы, rate limit, отклоненные секретные поля, аномалии публикаций.

UI Admin Panel показывает операционные сводки и безопасные ссылки. Полные журналы доступны только через систему наблюдаемости и соответствующие роли.

## Алерты

| Сигнал | Условие | Действие |
| --- | --- | --- |
| API не ready | readiness отсутствует дольше согласованного окна | проверить БД/auth и остановить рискованные публикации |
| Ошибка публикации | рост/серия ошибок или ноль успешных после релиза | проверить версии, транзакции, audit и rollback plan |
| Ошибка runtime API | рост 5xx или fallback продуктов | проверить API, ETag, БД и совместимость контракта |
| БД перегружена | высокий pool wait/ошибки/latency | ограничить нагрузку, проверить запросы и емкость |
| Интеграция деградирует | timeout/error выше порога | проверить endpoint/circuit breaker, не добавлять повторный storm |
| Возможная утечка | событие запрещенного поля или secret-like pattern | остановить распространение, провести security incident process |

Пороги и каналы эскалации устанавливаются для каждого окружения отдельно. Алерт должен содержать сервис, окружение, временной интервал, correlation/trace ссылки и runbook, но не секретные данные.

## Retention и проверка

Сроки хранения логов, трасс, метрик и аудита согласуются с политиками безопасности и комплаенса. Доступ регулярно ревизуется. Дашборды и алерты проверяются не только синтетикой, но и контролируемыми отказами: timeout integration, недоступность БД, конфликт публикации, fallback runtime-клиента и отказ central auth.
