# Обработка ошибок

## Принципы

- Ошибки имеют стабильный машинный код, понятное пользователю сообщение и correlation ID.
- Внешнему клиенту не возвращаются stack trace, SQL, токены, cookie, секреты или внутренние адреса.
- Ошибка никогда не маскируется ложным успехом или актуальным статусом.
- Изменяющие операции идемпотентны там, где повтор возможен из-за сети; публикация защищена ключом идемпотентности/версией черновика.
- Логи содержат технический контекст с редактированием чувствительных значений.

## Формат API-ошибки

```json
{
  "error": {
    "code": "CONFIG_VALIDATION_FAILED",
    "message": "Черновик не прошел проверку.",
    "details": [
      {"field": "services.crm", "reason": "Не пройдена проверка соединения."}
    ],
    "requestId": "req_..."
  }
}
```

`details` возвращается только если он не раскрывает чувствительную информацию и пользователь имеет право видеть поле. HTTP-статус соответствует классу ошибки.

## Каталог ошибок

| Класс | HTTP | Код | Поведение UI/API |
| --- | ---: | --- | --- |
| Некорректный ввод | 400/422 | `VALIDATION_FAILED` | показать поля и безопасные причины |
| Нет identity | 401 | `UNAUTHENTICATED` | перейти к входу или сообщить о сессии |
| Недостаточно прав | 403 | `FORBIDDEN` | не раскрывать защищенный объект |
| Нет объекта | 404 | `NOT_FOUND` | нейтральное сообщение без подсказки о чужих данных |
| Конфликт версии | 409 | `VERSION_CONFLICT` | предложить обновить diff и создать новый черновик |
| Лимит запросов | 429 | `RATE_LIMITED` | показать время безопасного повтора |
| Ошибка зависимости | 502/503/504 | `UPSTREAM_UNAVAILABLE` | показать последний известный статус, разрешить контролируемый retry |
| Внутренняя ошибка | 500 | `INTERNAL_ERROR` | безопасное сообщение и request ID |

## Правила по доменам

### Публикация

Перед публикацией сервер повторно проверяет права, состояние черновика, схему, отсутствие секретов, базовую версию и требуемые health-зависимости. При конфликте или сбое транзакции опубликованная версия не меняется. Пользователь видит diff-конфликт, а не автоматическое перезаписывание чужих изменений.

### Каталог интеграций

Ошибка вызова внешнего health endpoint нормализуется в краткий статус: DNS, connect, TLS, timeout, недопустимый HTTP-статус. Сырые request/response, `Authorization` и тело upstream не показываются UI. Превышение времени ограничивается тайм-аутом и не удерживает HTTP-запрос пользователя бесконечно.

### Runtime API

Если API временно недоступен, product frontend использует встроенные defaults и помечает диагностический сигнал локально при наличии такой возможности. Admin Panel не должен требовать от продукта аварийного получения конфигурации для базовой работы. `304 Not Modified` не является ошибкой.

## Поведение интерфейса

- Ошибка формы остается рядом с соответствующим полем и сохраняет безопасно введенные значения.
- Глобальная ошибка показывает текст, время, request ID и действие «Повторить» только для безопасных операций.
- После timeout изменяющей операции UI сначала запрашивает фактический статус по ключу идемпотентности, а не слепо повторяет публикацию.
- Неудачная health-проверка не изменяет конфигурацию сервиса.
- Ошибки по ролям не обходятся скрытием кнопки: сервер всегда выполняет авторизацию.

## Обработка на сервере

Все исключения проходят единый middleware: классификация, request ID, безопасное логирование, ответ по контракту и счетчик метрики. Необработанное исключение является `500`, логируется с трассировкой только в защищенный sink и не передается клиенту. Валидация выполняется до сетевых вызовов и транзакций, а транзакционные ошибки завершаются rollback.

## Инциденты

Рост `5xx`, ошибки публикации, аномальный `403`, исчерпание пула БД или массовые timeout интеграций создают алерт. Оператор использует request ID для связи UI-события, audit trail, логов и трассировки; запрещено просить пользователя присылать токены или полные заголовки запроса.
